Deploy the Cloud-AWS Hybrid Site

A site-to-site IPsec tunnel from dc-ce-1 (Cisco C8000v in EVE-NG) to a self-managed strongSwan EC2 in AWS, plus a scheduled Lambda that watches the tunnel from the AWS side. Eight commands, ~6–8 minutes, free-tier.

8 commands ~6–8 min Free-tier IPsec / IKEv2 16 security findings closed

What this builds

  • AWS side — t3.micro strongSwan EC2 (Ubuntu 22.04 LTS, IMDSv2-only) with EIP, Secrets Manager-backed PSK, custom SSM document with the swanctl --list-sas command hardcoded, IAM-scoped Lambda monitor with region+account conditions, two CloudWatch alarms via metric-math, SNS email alerts.
  • Lab side — a cloud_aws site in NetBox, an IPsec block on dc-ce-1 rendered from the spec, an MCP tool (cloud_tunnel_health) that reports IKEv2/IPsec state.
  • Pipeline — push-time PSK injection (scripts/push_configs.py) pulls the secret from AWS Secrets Manager at deploy time so the rendered config in configs/generated/dc-ce-1.cfg stays commit-safe.
  • State backend — S3 with customer-managed KMS CMK encryption, TLS-only bucket policy, versioned, public access blocked. DynamoDB lock table with PITR enabled.

Prerequisites

  • AWS account with the free tier active (or budget acceptance). The vpn module fits inside the 12-month free tier; the existing cloud-devops-pipeline dev env runs a NAT Gateway (~$32/mo) and ALB (~$16/mo) — destroy when not in use.
  • cloud-devops-pipeline repo cloned, referred to here as $AWS_REPO.
  • Terraform ≥ 1.5, AWS CLI v2, IAM creds with permission to create EC2, EIP, Secrets Manager, IAM, Lambda, CloudWatch, SNS, EventBridge, KMS, SSM (including custom Documents), S3, DynamoDB.
  • Lab is already populated: make generate-spec succeeds against the 21-node baseline; dc-ce-1 is reachable via SSH from this host; NetBox is up.
  • A reachable public IP for IKE ingress — the strongSwan SG only allows UDP 500/4500/ESP from this /32. Validated regex rejects anything that isn't a literal IPv4 dotted quad.

Build sequence

The full deploy is eight commands, ~6–8 min total. Click the checkbox on each step as you complete it — your progress persists across reloads.

0 / 8 complete
1

Bootstrap the state backend (one-time per account)

The S3 bucket and DynamoDB lock table that hold Terraform's state can't manage themselves with Terraform — chicken-and-egg. The bootstrap script captures that out-of-band step as code:

Bash
bash $AWS_REPO/scripts/bootstrap-state-backend.sh

Idempotent — safe to re-run. Creates a customer-managed KMS CMK with annual rotation, applies SSE-KMS to the state bucket, applies a TLS-only + non-KMS-deny policy, re-asserts versioning + public-access-block, enables Point-In-Time Recovery on the DynamoDB lock table.

i
Why this matters: every random_password in the modules — including the IPsec PSK — lands in terraform.tfstate in cleartext. State at rest MUST be CMK-encrypted, not just SSE-S3, so we control the key policy, rotation, and CloudTrail audits per-key.
✓
2

Apply AWS side

Bash
cd $AWS_REPO/terraform/environments/dev
terraform init   # picks up the kms_key_id in the backend block
terraform apply \
  -var enable_vpn=true \
  -var onprem_public_ip=<your.public.ip> \
  -var vpn_alert_email=<you@example.com>

Apply finishes when null_resource.strongswan_ready clears (~75 sec on Ubuntu — the gate polls SSM until systemctl is-active strongswan-starter returns active). You'll get an SNS subscription confirmation email — click it. Without confirmation, alerts fire silently.

!
Secret in 7-day recovery? A previous destroy schedules vpn/onprem-psk for deletion. To re-apply within 7 days, force-delete it first:
Bash
aws secretsmanager delete-secret --secret-id vpn/onprem-psk --force-delete-without-recovery
✓
3

Pull AWS outputs into the lab

Bash
cd $LAB_REPO        # back to Eve-NG_Agent
make sync-aws-outputs

Writes .aws_outputs.json (gitignored — contains the strongSwan EIP and PSK secret ARN, not the secret itself). Then export them into your shell:

Bash
export AWS_STRONGSWAN_EIP=$(jq -r .strongswan_eip.value < .aws_outputs.json)
export AWS_VPN_PSK_SECRET_ARN=$(jq -r .psk_secret_arn.value < .aws_outputs.json)
✓

Validate (Batfish digital twin)

Bash
make validate-batfish
!
Known coverage gap. Batfish does not model Cisco IKEv2/IPsec crypto blocks, so a green validate-batfish does NOT confirm the IPsec tunnel will come up. Ground truth comes from cloud_tunnel_health in step 7.
✓
7

Push to dc-ce-1

Bash
export API_AUTH_TOKEN=<the-bearer-token-for-the-API>   # only if pushing through API
make push-configs DEVICE=dc-ce-1

scripts/push_configs._inject_aws_psk reads AWS_VPN_PSK_SECRET_ARN, fetches the secret from AWS at this exact moment, substitutes the marker in memory, sends to the device. The plaintext PSK never lands on disk.

✓

Cross-confirm the tunnel state

Wait ~30 sec for IKE to negotiate, then:

Bash
ssh dc-ce-1 'show crypto ikev2 sa | include READY'
✓

Verification — four independent signals

Every method can lie in a different way. All four should agree before you call it done.

Signal A · Device

show crypto on dc-ce-1
IKEv2 SA in READY state, ESP SAs installed inbound + outbound, packet counters incrementing.
ssh dc-ce-1 'show crypto ikev2 sa detail'

Signal B · MCP tool

cloud_tunnel_health (agent's view)
Hand-rolled parser + defensive contract — never returns None; UNKNOWN if parser empty.
cloud_tunnel_health(device="dc-ce-1")

Signal C · Lambda

aws lambda invoke (cloud-side view)
Two-metric design: CheckSucceeded + TunnelEstablished. Composite alarm fires only when Check=1 ∧ Established=0.
aws lambda invoke --function-name cloud-devops-vpn-monitor /tmp/out.json

Signal D · Data plane

Live RTT integration test
Pings AWS VPC private IP from dc-ce-1's Loopback0; asserts RTT < 500 ms; tears down.
EVE_LIVE=1 pytest tests/integration/test_cloud_tunnel_pipeline.py -v

Reboot survival

Reboot the strongSwan instance and confirm the tunnel returns:

Bash
aws ec2 reboot-instances --instance-ids "$INST"
sleep 180
ssh dc-ce-1 'show crypto ikev2 sa | include READY'

The vpn-bootstrap.service systemd unit re-fetches the PSK from Secrets Manager and re-renders /etc/swanctl/swanctl.conf on every boot, so reboot is non-destructive.

Security posture — what's enforced

Every fix from the security review is wired in. 16 findings, 16 closures.

Push-time PSK
Plaintext PSK never committed
scripts/push_configs._inject_aws_psk fetches at deploy. PSK character set excludes " $ ` \ so heredoc rendering can't be subverted.
Input validation
onprem_public_ip regex-validated
Rejects anything that isn't a literal IPv4 dotted quad — closes the shell-injection surface in user_data.
Lambda IAM · M3
Custom SSM document, never RunShellScript
ssm:SendCommand ONLY on the strongSwan instance ARN AND a custom aws_ssm_document with swanctl --list-sas hardcoded. AWS-RunShellScript is NOT in the policy — a future code change can't broaden blast radius without a Terraform diff.
Lambda IAM · L7
Region + account conditions
cloudwatch:GetMetricStatistics and ssm:GetCommandInvocation conditioned on aws:RequestedRegion AND aws:PrincipalAccount. (aws:SourceAccount doesn't apply to direct API calls — that key is for service-to-service.)
Lambda IAM · parity
IAM_REQUIRED meta-test enforces lockstep
handler.py:IAM_REQUIRED is asserted in lockstep with the Terraform IAM via test_iam_dependencies_documented — AST-walks every boto3.client(...).method(...) call. Drift fails CI.
State at rest
Customer-managed KMS CMK
S3 backend uses CMK with annual rotation. Bucket policy denies non-TLS uploads AND explicitly-non-KMS uploads (StringNotEqualsIfExists). DynamoDB lock table has PITR.
EC2 metadata
IMDSv2 only
http_tokens = required. Token theft via SSRF is prevented.
Network scoping
strongSwan SG + IPsec TS scoped
SG ingress locked to <onprem_public_ip>/32 on UDP 500 / UDP 4500 / ESP. IPsec traffic selectors scoped to VPC CIDR ↔ onprem CIDRs (NOT 0.0.0.0/0) so internet-bound traffic bypasses IPsec — keeps SSM agent connectivity alive.
Reboot determinism
vpn-bootstrap systemd unit
Type=oneshot, Before=strongswan-starter.service — re-fetches PSK and re-renders swanctl.conf on every boot. PSK rotation just needs a unit restart on this host.
Two-metric alarming
Lambda failure ≠ tunnel failure
Composite alarm tunnel_down fires on Check=1 AND Established=0 via metric-math. Lambda failure does NOT page on-call. Separate lambda_broken alarm on CheckSucceeded Sum < 1 over 30 min catches the Lambda itself.

Teardown

Bash
cd $AWS_REPO/terraform/environments/dev
terraform destroy \
  -var enable_vpn=true \
  -var onprem_public_ip=<same.IP> \
  -var vpn_alert_email=<same.email>

Persistent state (survives destroy):

  • S3 state bucket + KMS CMK + DynamoDB lock table (created by bootstrap-state-backend.sh)
  • AWS Budget alarm (created manually)
  • The lab side — Eve-NG_Agent repo, NetBox data, dc-ce-1 templates — untouched
i
The Secrets Manager secret enters a 7-day recovery window. Re-applying within 7 days requires aws secretsmanager delete-secret --secret-id vpn/onprem-psk --force-delete-without-recovery first.

Troubleshooting

11 failure modes hit during the actual security-fix re-deploy. Each one tied to a specific cause and one-line fix. Search by symptom, error message, or component.

11 issues
terraform apply errors with AccessDenied: explicit deny in resource-based policy on state upload›
CauseBackend block missing kms_key_id — terraform sends AES256 which the state-bucket policy denies.
FixConfirm kms_key_id = "alias/cloud-devops-pipeline-tfstate-key" is in the backend "s3" block; re-init with -reconfigure.
null_resource.strongswan_ready times out at 5 min, cloud-init log shows Failed to enable unit: Unit file strongswan-swanctl.service does not exist›
CauseWrong service name — Ubuntu 22.04's strongswan-swanctl package only ships the swanctl binary, not a service unit.
FixCurrent user_data uses strongswan-starter.service; confirm via cat terraform/modules/vpn/user_data.sh.tftpl | grep enable.
Lambda returns AccessDeniedException ... no identity-based policy allows ssm:GetCommandInvocation›
CauseIAM condition uses aws:SourceAccount (which doesn't populate for direct API calls).
FixConfirm conditions use aws:PrincipalAccount; terraform apply to update.
Lambda returns ssm_error ... command stuck in Pending after 25s then SSM agent goes ConnectionLost›
CauseIPsec traffic selectors are 0.0.0.0/0 — kernel xfrm policy captures ALL outbound traffic on the strongSwan box, including SSM agent's TLS connection to ssmmessages.<region>.amazonaws.com.
FixScope local_ts/remote_ts in swanctl.conf to VPC CIDR ↔ onprem CIDRs; replace EC2.
make push-configs errors IAM principal lacks secretsmanager:GetSecretValue›
CausePush host's IAM principal differs from the one that created the secret.
FixSet AWS_PROFILE, or grant secretsmanager:GetSecretValue on vpn/onprem-psk to your principal.
make push-configs errors AWS_VPN_PSK_SECRET_ARN is not set›
CauseForgot to export from .aws_outputs.json.
Fixexport AWS_VPN_PSK_SECRET_ARN=$(jq -r .psk_secret_arn.value < .aws_outputs.json)
cloud_tunnel_health returns ike_state: "UNKNOWN"›
CauseHand-rolled parser couldn't match the device output.
FixCapture result["raw"]["ikev2"], file as a regression sample under tests/fixtures/.
show crypto ikev2 sa shows IN-NEG then nothing›
CausePSK mismatch between sides.
FixRun rotate-aws-vpn-psk.md — most common cause is a stale dc-ce-1 keyring after redeploying AWS.
show crypto ikev2 sa shows READY but ping fails›
CauseAsymmetric routing — return path missing on AWS side.
Fixaws ec2 describe-route-tables --route-table-ids <private-rt> — every onprem CIDR should point at the strongSwan ENI.
Lambda CheckSucceeded consistently 0, SSM Pending›
CauseSSM agent on strongSwan unreachable (likely IPsec capture or SG/route issue).
FixSSM-Session into the box (aws ssm start-session --target $INST); check journalctl -u amazon-ssm-agent, swanctl --list-policies.
Alarm fires for tunnel-down but show crypto says READY on dc-ce-1›
CausestrongSwan side down or swanctl --list-sas returns empty.
FixSSM-Session, run swanctl --list-sas; check journalctl -u vpn-bootstrap and journalctl -u strongswan-starter.
terraform apply blocked with SecretAlreadyScheduledForDeletion›
CauseRe-applying within 7 days of destroy.
Fixaws secretsmanager delete-secret --secret-id vpn/onprem-psk --force-delete-without-recovery then retry.
